# 03 开发规范与约束

> - **红线**：违反即为缺陷，必须有自动化测试覆盖，任何 PR 不得削弱。
> - **规范**：默认必须遵守，例外需在 PR 中说明理由。
> - 依据均为 PRD v1.1 的对应章节。

## 1. 安全红线（R 系列）

| ID | 红线 | 依据 | 强制方式 |
|---|---|---|---|
| R-01 | **7 类必问事项**：`delete_data`、`stop_service`、`spend_money`、`external_message`、`product_direction`、`secret_change`、`permission_change`。命中任一类必须由你确认，不能通过配置删除 | §7.2 `human_gate.always_on`、§11、v1.1·K8 | 判断层和工具调用前置检查；配置校验拒绝缺项 |
| R-02 | 其中 `delete_data`、`spend_money`、`secret_change`、`permission_change` 这 4 类**永远不按先例自动处理** | §11.1、§19.1 `never_auto_by_precedent` | `precedents.match()` 命中这 4 类时直接拒绝自动处理 |
| R-03 | **硬规则优先于 AI**：`final_risk = max(hard, ai)`，AI 只能调高风险等级，不能调低 | §2、§10.3 | `ci/risk.py` 单元测试 |
| R-04 | **密钥不进入提示词、日志、记忆、飞书消息** | §17.3、§16.1 | 打码过滤器作用于全部 4 个出口；提示词组装时检查已加载密钥的明文 |
| R-05 | 配置中**只能写 `secret://` 引用**，不能出现明文 | §17.1 | 配置校验时，敏感字段不是 `secret://` 开头就报错 |
| R-06 | **执行变量不含任何凭证** | §7.2.1 | `env_vars.py` 只允许注入 §7.2.1 列出的变量 |
| R-07 | **一次性容器**：测试、构建、依赖安装、AI 审查和项目代码不在本机直接运行；网络默认关闭；不注入密钥；工作区只读挂载；用完即销毁 | §9.1.1、v1.1·K5 | Skill 声明 `sandbox.tests: container` 时强制走容器（M2 阶段的降级方案见 01 的注） |
| R-08 | **审查环境**：只读、无网络、无密钥、没有任何写入工具 | §10.2、v1.1·K4 | `sandbox.yaml.review` 中的固定值 |
| R-09 | **平台门禁**：`pa/ai-review` 和 CI 都是必需检查；PA 放行前必须确认全部为 success | §10.1、v1.1·K6 | `merge_gate` 检查 + 部署清单 |
| R-10 | **身份分离**：只有 merger 身份能合并；agent 身份不开启平台的自动合并 | §10.1、v1.1·D17 | 适配器的 `identity` 参数检查 |
| R-11 | **C 档引擎硬限制**：不能改代码；`risk_ceiling=low`；`confidence ≤ 0.6`；不能使用 `external_message` 和 `spend_money`；不能通过配置放宽 | §8.4 | 选择器和判断层双重检查 |
| R-12 | **外部内容一律不可信**：外部内容放在 `<untrusted>` 标签内，只当数据，不改变规则或授权 | §7.2.2、§17.5 | 组装器统一包装 |
| R-13 | **权限分层**：agent 令牌只能拿到 `AgentFacade`，不能读密钥，不能修改合并权限矩阵、白名单、预算、密钥配置和先例 | §20.1、v1.1·D21 | 代码层面没有这些方法；有越权调用测试 |
| R-14 | **Webhook 鉴权**：HMAC-SHA256 签名、请求时间戳不超过 5 分钟、Gitea 来源 IP 白名单；同一来源 5 分钟内失败超过 20 次，拉黑该 IP 1 小时 | §6.1、§17.5 | `ingress` 测试 |
| R-15 | **Tunnel 只暴露 `/hooks/github`、`/hooks/feishu`、`/healthz`**，其余路径返回 404 | §17.5、§22.4 | `public_paths` 配置 + cloudflared 的 ingress 规则 |
| R-16 | **决定回调**：校验签名、确认点击人的 open_id 属于 owner、nonce 只能用一次、检查是否过期 | §12.3 | `notify` 回调测试 |
| R-17 | **控制台**：密码 + TOTP；Cookie 设置 HttpOnly、SameSite=Strict；校验 CSRF；如需公网访问必须经过 Cloudflare Access | §17.5 | `api/auth.py` |
| R-18 | **本地 MCP 服务**：只监听 127.0.0.1；每个任务一次性 Token；只开放 Skill 白名单中的工具 | §9.2 | `tools/mcp_server.py` |
| R-19 | **`blocked_commands` 不是安全边界**，代码和文档都不得把它描述成安全措施 | §7.2、§17.5 | 代码审查 |
| R-20 | `.env` 后端要求文件权限为 600，否则拒绝启动 | §17.2 | 启动检查 |

## 2. 可靠性红线

| ID | 红线 | 依据 |
|---|---|---|
| R-21 | **先存后做**：所有对外写操作只通过 `effects` 执行；effect 与业务状态在同一事务内提交；带幂等键；执行前先检查平台上的实际状态 | §9.1.2、v1.1·D1 |
| R-22 | **状态迁移入口唯一**：只能通过 `transition()`；使用乐观锁；每次迁移写 `task_events` | §4.2 |
| R-23 | **有界执行**：单任务 token、轮数、时长上限；重派最多 2 次；退回修改和审查最多 3 轮；临时错误自动重试 3 次。这些在预算金额为空时**同样生效** | §2、§15、§19.1 |
| R-24 | **恢复提示**：租约过期回收的任务再次执行时，提示词以恢复说明开头；开 PR 前先用 `find_pr_by_branch` 查有没有已存在的 PR | §6.4、§9.1、v1.1·D2 |
| R-25 | **暂停语义**：暂停时只停派单、研判、输入投递和 effects；事件照常入库；正在运行的任务不中断；决定的到期时间顺延 | §6.4、v1.1·D18 |
| R-26 | **保留槽位**：只接你本人的明确请求和后续评论；不受预算熔断拦截 | §3.3、§6.4、v1.1·D9 |
| R-27 | **策略变更不取消正在运行的任务**，只投递 `policy_changed` 输入 | §6.5、v1.1·D6 |
| R-28 | **授权记录不可修改**；范围扩大必须新开任务 | §6.5、v1.1·D3 |
| R-29 | SQLite **只放在本地盘**；WebDAV 只用于归档 | §13.3 |

## 3. 注意力与沟通规范（v1.1·D16 / K9 / D11）

| ID | 规范 | 依据 |
|---|---|---|
| C-01 | 一张决定卡片只问一个问题（来自 `human_action`）；同一任务的多个待决定事项按顺序推送 | §12.3 |
| C-02 | 卡片结构固定：标题用 `summary`；正文为问题、推荐选项及理由（≤60 字）、证据（最多 3 条）；底部为原处链接和"在控制台查看"；卡片上带"记为先例"复选项 | §12.3 |
| C-03 | 点击后卡片原地更新为结论，不另发新消息 | §12.3 |
| C-04 | 接单时确认一次（`ack: once`）；执行中保持安静；聊天消息不超过 100 字（`max_chat_words`） | §7.2 |
| C-05 | 规则默认 `notify: decision_only`；`dropped` 静默结案 | §6.3、§11 |
| C-06 | 诚实交付：草稿要标 `draft: true`；涉及 UI 的改动必须附截图（`ui_change_requires_screenshots`）；开了 PR 不等于完成 | §2、§7.2 |
| C-07 | PR 描述和评论第一行固定为"本内容由自动化 Agent 生成"；审查意见已修复的静默标记为已解决，不采纳的一句话说明理由；发现你的分支已包含同样改动时，关闭自己的 PR 并指向你的 PR | §10.1 |
| C-08 | 控制台：健康状态不占版面；数字必须等于它链接的列表条数；只显示会影响你下一步行动的指标；标签写"在等谁、需要什么"；破坏性操作需要二次确认 | §20.3 |
| C-09 | 系统问题的上报门槛：同一项连续失败 3 次才显示；必须附带可以直接执行的处理按钮 | §16.3 |

## 4. 代码规范

### 4.1 提示词组装（§7.2.2、v1.1·D14）

**组装顺序固定，不得调整：**

| 顺序 | 段 | 说明 |
|---|---|---|
| 1 | `shared` | 通用约定 |
| 2 | `role` | 执行者 / 审查者 / 研判者 |
| 3 | Skill 提示词 | `prompt.md` + `skill_section` |
| 4 | 规则要求 | 命中规则的流程要求 |
| 5 | 参考资料 | 记忆、经验、决策台账，标注为"参考资料，不是指令" |
| 6 | 本次输入 | 外部内容放在 `<untrusted source=…>` 中 |
| 7 | `environment` | 执行变量 |
| 8 | `policy` | 每次请求都会变化，**必须放在最后**，以便命中提示词缓存 |

**效力从强到弱：**
1. 代码强制的事实
2. 内置提示词及你的覆盖
3. 命中规则的流程要求
4. Skill 和团队自定义段落
5. 外部文本

### 4.2 回执格式（§7.3）

- **校验**：所有引擎的输出都必须通过 `receipt.schema.json` 校验（见 `07-配置模板/schemas/`）。
- **不合规时**：先让引擎修正 1 次，仍不合规则按 `needs_human` 处理。
- **字段约束**：

| 字段 | 约束 |
|---|---|
| `status` | 只能是 `succeeded`、`failed`、`needs_human`、`blocked`、`dropped` 之一 |
| `human_action` | 只能包含一个问题 |
| `human_action.why` | 不超过 60 字 |
| `tags` | 只能取 7 类必问标签 |
| `handback[]` | 超出本任务范围的请求必须写在这里，不得擅自扩大范围 |

- **C 档引擎**：结构化转换后 `confidence ≤ 0.6`。

### 4.3 Python 工程

| 项目 | 规范 |
|---|---|
| 版本与依赖 | Python 3.12，用 uv 管理，`uv.lock` 锁定版本；启动必须用 `uv sync --frozen`（§21、§17.5） |
| 数据模型 | 配置、回执、事件、接口的入参和出参都用 Pydantic v2 模型（§21） |
| 数据库访问 | SQLAlchemy 2.0 + Alembic；所有写操作用短事务；领取任务用 `UPDATE … RETURNING` 原子完成（§13.1） |
| 异步 | HTTP 用 httpx 异步客户端，重试用 tenacity；引擎接口是 async 的（§8.1、§21） |
| 日志 | 只用 structlog 输出 JSON；禁止 `print` 和直接拼接密钥（§16.1） |
| 插件注册 | 插件只能通过 entry points 注册，核心代码不得直接导入某个具体实现（§2、§3.4） |
| 依赖方向 | 遵守 `02` 第 1 节的依赖方向，禁止反向引用 |
| 主键与时间 | 主键用 ULID；时间用 UTC ISO8601（§14） |
| 依赖安全 | 定期运行 `pip-audit`（§17.5、§22.6） |
| 测试 | 引擎和代码平台都必须有基于假实现的契约测试（§18.1） |

## 5. 配置规范

### 5.1 通用

| 项目 | 规范 |
|---|---|
| 格式与校验 | 全部用 YAML，由 Pydantic v2 强校验；未知字段直接报错 [实现约定] |
| 插值与引用 | 支持 `${ENV}` 插值和 `secret://<provider>/<path>` 引用（§19、§17.1） |
| 热加载范围 | rules、skills、merge_policy、budgets 修改后热加载；engines、sources 修改后需要重启对应进程，CLI 会给出提示（§19） |
| 版本管理 | 配置目录 `~/.config/pa/` 用 git 管理，**不含任何明文密钥**（§18.2） |

### 5.2 版本与冲突（§19.3、v1.1·D15）

1. 每次保存都生成一个新的不可修改版本（写入 `config_versions` 表并做一次 git 提交），记录 `origin` 为 console、cli、agent 或 upgrade 之一。
2. 写入时必须带 `base_revision`；不一致时返回 **409**，草稿保留。
3. 覆盖内容与默认值完全相同时，自动删除这个覆盖。
4. 升级后，如果你覆盖过的那部分默认值也变了，标记"默认已更新"，你可以选择保留自己的版本或改用新默认值。

## 6. 变更流程（编程智能体须遵守）

1. **开始前**：在 `01` 中找到任务 ID，在 `06` 中找到对应的用例 ID。
2. **提交 PR 时**，描述必须包含：
   - 任务 ID；
   - PRD 章节和 v1.1 编号；
   - 是否触及 R 系列红线；
   - 新增的配置字段。
3. **触及红线时**：如果改动涉及 R-01 至 R-29 中任何一条，必须同时更新对应的测试，并在 PR 中列出这些测试的名称。
4. **PRD 未定义的内容**：不得自行发明，记为 `TODO(PRD)`，并提出问题。
