## 优先处理的问题（P1）

### R04：MCP 未配置判断器时，需审批的工具直接执行

- 位置：`src/pa/tools/mcp_server.py:54`。
- `gates` 非空时，仅在 `self.judge is not None` 才检查审批；缺少 judge 会落到 executor。
- 复现：使用真实 `sample-direct` 白名单调用 `feishu_notify`，未配置 judge，
  测试 executor 被调用，返回 `result` 而不是 `needs_approval`。没有实际发送消息。
- 修复方向：需要审批且判断器缺失时拒绝执行，审批通过后才能调用 executor。

### R05：进程回退后端可以写审查工作区，并继承凭证，却记录 review=strict

- 位置：`src/pa/sandbox/runtime.py:94`、`:99`、`:103`；
  `src/pa/sandbox/backends.py:56`。
- `mount=readonly`、`network=none`、`review=strict` 仅进入 notes，
  `subprocess.run` 没有实现挂载、网络或文件访问隔离。
  环境变量只按少数前缀排除，仍继承 `GITHUB_TOKEN` 等凭证以及宿主 HOME。
- 两条复现：`review_spec` 下子进程把临时工作区文件从 `original` 改为 `changed`，
  结果仍为 `ok=True` / `review=strict`；注入假的 `GITHUB_TOKEN` 哨兵值后，
  子进程能读取其存在性。未读取或输出真实凭证。
- 修复方向：严格审查必须使用实际隔离后端；没有可用后端时阻止严格审查，
  不能以 notes 作为隔离成立的证据。环境使用最小许可清单。

### R01：跨文件保存配置发生版本主键冲突，失败后磁盘已变化

- 位置：`src/pa/config/versions.py:123`；表定义在
  `alembic/versions/0001_initial.sql:52`。
- `current_revision` 按文件计算版本，但数据库 `revision` 是全表唯一主键。
  第一次保存第二个文件也会插入 revision=1。
- 复现：先保存 `notify.yaml` 成功，再首次保存 `principals.yaml` 返回 HTTP 500。
  第二个文件已经写入新的 owner 配置，数据库版本记录因主键冲突回滚。
- 修复方向：通过新迁移统一全局版本或使用 `(file, revision)` 唯一约束，
  同时处理文件写入成功、数据库提交失败时的恢复，避免配置与审计分离。

### R17：API 成功禁用规则后，下一条事件仍按旧规则创建任务

- 位置：`src/pa/api/app.py:419`、`src/pa/store/facades.py:70`。
- 配置写接口只持久化文件；长生命周期 OwnerFacade 的 `self.config` 未更新，
  `emit()` 仍把旧快照传给 ingest。
- 复现：PUT `rules.yaml` 禁用全部规则，返回 200，重新从磁盘加载也确认全部禁用；
  随后同一应用 POST `/api/v1/events` 仍创建任务。
- 修复方向：提交后原子替换已验证的活动配置，并对相关运行组件触发策略更新。
  不能仅依赖 worker 自己重新 load；它会继续领取已按旧配置创建的任务。

### R06：SCM 检查结果与合并门禁不兼容，且 GitHub 检查遗漏 AI 审查状态

- 位置：`src/pa/ci/merge_gate.py:22`、`src/pa/scm/github.py:93`；
  状态写入位置 `src/pa/scm/github.py:162`。
- 第一条复现：把适配器契约中的 `CheckSummary(state='success')` 传入 merge_gate，
  立即触发 `AttributeError: ... all_required_passed`。
  既有门禁测试使用自定义 stub，未覆盖真实 CheckSummary。
- 第二条复现：平台模拟返回 CI check-run 成功、`pa/ai-review` commit status 失败；
  `get_checks` 只读取 check-runs，返回 `state='success'`。
  仓库自身的 set_status 写的是 commit statuses，读取与写入渠道不一致。
- 修复方向：统一检查结果类型，汇总两种状态来源并核对必需检查名称及当前 SHA；
  缺失、等待或失败的必需检查都应阻止自动合并。

### R02：控制台登录成功后，取消和回答决定仍返回 401

- 位置：`src/pa/console/static/console.js:11`、`:34`、`:42`；
  `src/pa/api/app.py:121`。
- 浏览器通过签名 Cookie 登录，JS 给 API 请求附加 CSRF；写接口只接受 Bearer。
  登录返回的 csrf 也没有被登录页保存到 JS 读取的 `pa_csrf` Cookie。
- 复现：真实 LoginService 登录成功、总览返回 200，携带会话 Cookie 和有效 CSRF
  调用取消接口，返回 401 `invalid or missing bearer token`。
- 修复方向：提供校验会话和 CSRF 的浏览器写入口，正确传递 CSRF；
  保持独立 Bearer API 的权限边界，不向浏览器暴露 owner token。

### R03：正式 HTTP 启动入口没有接入控制台登录服务

- 位置：`src/pa/procs/server.py:21`、`src/pa/api/app.py:605`。
- `serve_http` 没有读取 console.enabled/auth、解析凭证或创建 LoginService，
  而 create_app 只在显式传入 login_service 时挂载控制台。
- 复现：配置 console.enabled=true 及有效的 secret 引用，捕获真实 serve_http
  传给 uvicorn 的应用；访问 `/console/login-page` 返回 404。
- 修复方向：启动时按配置创建登录服务并挂载路由，补充从配置到 HTTP 页面的一体测试。

### R07：新增代码 Skill 不会被主 worker 领取

- 新功能位置：`src/pa/skills/assets/sample-code/skill.yaml:10`；
  运行阻断位置：`src/pa/procs/worker.py:76`。
- `_queue_candidates` 仍硬编码 `skill_id='sample-direct'`；新增 `sample-code`
  和 `weekly-cleanup` 均无法走现有执行器。CI/workspace 模块也没有被主 worker 调用。
- 复现：新增合法手动规则并发出 sample-code 任务，使用健康假引擎执行 Worker.once，
  返回 None，引擎调用次数为 0，任务保持 queued。
- 修复方向：先接通 code 模式的工作区、执行、PR、审查和 CI 状态驱动链路，
  再允许该模式参与派单，不能只删除 SQL 过滤后按文本路径直接结案。
- 这是新增功能没有接入既有执行链路，不是声称原有文本任务发生回归。

### R08：货币预算计算已存在，但没有接入实际派单和调用

- 新功能位置：`src/pa/cost/budget.py:81`；
  接线位置：`src/pa/engines/selector.py:93`、`src/pa/procs/worker.py:50`。
- selector 只在调用方传入 budget_allows 时检查金额预算，worker 没有传入。
  新增 check_budgets / budget_action 没有实际运行时调用方。
- 复现：创建推断型 cron/auto 任务，避免明确请求的保留槽豁免歧义；
  给 fake 引擎设置 0 元预算，check_budgets 确认 blocked，worker 仍调用引擎并 closed。
- 修复方向：在首次派单、切换与每次调用前执行预算门禁，并把实际计价记入账本。
  此处金额预算失效与原有 token/轮数/时间累计限制是两回事。

### R09：回答“重试”只修改决定记录，任务永久留在 awaiting_decision

- 位置：`src/pa/api/app.py:341`。
- 端点只把 decisions 标为 answered 并写 audit；未产生 decision.submitted 事件、
  未重新排队，也未触发决定执行器。
- 复现：对 awaiting_decision 任务回答其合法选项 retry，API 返回 200；
  再运行 worker 后任务仍等待决定，事件表内 decision.submitted 数量为 0。
- 修复方向：通过共同的决定处理链路校验选项、有效期与并发状态，
  同事务记录答案及后续动作，验证 retry / reject / take_over 的实际任务结果。

### R11：已过期先例仍可自动命中

- 位置：`src/pa/judge/precedents.py:163`、`:191`。
- 查询和命中判断都没有排除 expires_at 已过期的记录。
- 复现：插入 2000 年已过期的 prod 先例，再以相同问题查询，仍返回 hit / similarity=1。
- 修复方向：检索与应用前均检查有效期，避免过期授权绕过当前人工决定。

### R14：GUI 健康检查使用测试驱动，C 档权限读取层级也不正确

- 位置：`src/pa/engines/gui/engine.py:38`、`src/pa/engines/gui/limits.py:24`。
- 第一条复现：没有实际 macOS driver，app_path 指向不存在路径，health 仍返回
  installed=true，因为默认 SyntheticDriver.available=true。
- 第二条复现：对真实 SkillSpec 设置 risk_ceiling=low，保留 permissions.repo_write=true，
  C 档校验未拒绝，因为它读取 skill.repo_write，实际字段位于 skill.permissions。
- 同时，worker 调用 engine.run(request) 不传 skill，GuiEngine 默认 skill=None 会被
  risk_ceiling 校验拒绝；其成功分支也未把读取文本转换为 EngineResult.receipt。
- 修复方向：生产默认不可用，测试驱动必须显式注入；按真实 SkillSpec 检查权限，
  接通 skill 传递、全局 GUI 锁和结构化回执后再声明可派单。

### R16：仓库写锁 await 一次后并没有取得锁

- 位置：`src/pa/workspace/mirror.py:81`。
- async acquire 内直接 return lock.acquire()，返回另一个 coroutine，没有 await。
- 复现：`await RepoWriteLock.acquire('owner/repo')` 后底层 Lock.locked() 仍为 False。
- 修复方向：在方法内 await 底层 acquire，验证两个任务对同一仓库确实互斥，
  并保证异常/取消路径释放锁。

### R10：GitHub App 令牌刷新包装器递归调用自己

- 位置：`src/pa/scm/http.py:106`。
- 覆盖 client.request 后，wrapped 又调用 client.request，形成自递归。

### R12：熔断器第一次暂时失败就打开

- 位置：`src/pa/obs/breaker.py:55`、`:63`。
- FAIL_THRESHOLD / WINDOW_MIN 没有用于计数；closed 状态直接写 open。
- 复现：对没有历史健康记录的 fake 引擎调用一次 record_failure，立即返回 open。
- 修复方向：持久记录窗口内失败数，并将成功/失败记账接入 worker，满足 3 次/30 分钟条件。

### R13：API 允许的新增枚举与数据库 CHECK 不兼容

- 位置：`src/pa/api/app.py:62`、`:71`；
  `alembic/versions/0001_initial.sql:59`、`:62`。
- BudgetInput 允许 scope=task，但 SQL 只允许 global/skill/engine；
  MemoryInput 允许 kind=profile，但 SQL 没有 profile。
- 两条复现：在全量迁移后的库 PUT task 预算、POST profile 记忆均返回 500。
- 修复方向：增加迁移或收窄 API 枚举，并验证安装升级后的真实表约束。

### R15：任意 FTS 命中会把所有记忆都评分为 1

- 位置：`src/pa/memory/store.py:121`。
- 每行评分时执行的 FTS 查询只匹配 query，没有限制当前行 rowid。
- 复现：存在 deployment 和 unrelated 两条先例时，查询 deployment 会把二者都返回。
- 修复方向：先获取 FTS 命中的记录及分数，再与对应 memories 记录关联；
  不要用全库是否存在命中给每一行评分。

没有进入主事件/执行链路；旧 ingest 的模型研判 TODO 仍在，主运行时没有调度新增的
健康、清理、备份与轮换逻辑。这里仅报告接线事实，不声称已逐项完成这些模块的
所有边界测试。真实 GitHub/Gitea/Lark、桌面 GUI、容器隔离和整机恢复仍待独立验收。

建议先修复配置事务/生效、审批与隔离边界，再打通真实类型之间的调用和决定恢复，
最后用入口到最终状态的集成测试替换“测试代码自行串联函数”的验收方式。
